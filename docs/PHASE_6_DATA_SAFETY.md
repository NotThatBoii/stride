# Phase 6 data-safety review

This review covers the client paths that remove or replace study data. It accompanies [Phase 6 release hardening](PHASE_6_HARDENING.md). The server schema, RLS, change feed, tombstones, and operation receipts are unchanged and unpruned.

## Recovery and sync issues

Settings now includes an account-scoped **Recovery and sync issues** area beneath cloud synchronization. It shows pending changes, changes awaiting confirmation, failed changes, unresolved-conflict links, preserved copies, the last successful synchronization, and a persisted safe error summary. Lists start with twenty items and can show more. Failed changes appear first.

**Inspect change** shows the current record and the applicable recovery action. **Inspect copy** shows readable study history, notes, recorded allocation days, and paused timer information. Invalid copies remain stored and exportable even when an importable study-history subset cannot safely be inferred. No dismiss, delete-copy, reset-workspace, or cleanup control is provided.

A preserved copy that validates as study history can be exported as a regular Stride version 1 study backup or opened in the existing reviewed import dialog. That dialog still requires a successful backup download and completed cloud reconciliation before an additive import. Identity collisions retain both versions for explicit review.

## Failure handling and repairs

| Condition                                                                                                                   | Preserved state and behavior                                                                                                                                                                            |
| --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Offline connection, timeout, rate limit, or temporary server failure                                                        | Local records and the outbox remain intact. The worker retries with bounded backoff; a dispatched request keeps its original UUID and body. Rate-limit deadlines still apply to manual synchronization. |
| Authentication failure                                                                                                      | Local data remains in its account database. The account needs attention; no request is reassigned to another account.                                                                                   |
| Concurrent version or parent deletion conflict                                                                              | Both versions and recovery context remain available in the existing conflict interface. Submitted requests must first settle their original receipt unless a definitive rollback is known.              |
| Invalid never-submitted operation                                                                                           | The operation and its failure are preserved, the operation is quarantined, and unrelated valid changes can continue. Repeated **Sync now** calls do not clear quarantine.                               |
| Proven PostgreSQL validation/constraint rollback                                                                            | The original frozen request remains preserved. An explicit recovery action may rebuild the current validated record under a new UUID. No server receipt is assumed to exist.                            |
| Malformed acknowledgement or other uncertain submitted result                                                               | The request stays frozen. A selected, backup-gated retry sends the same UUID and body. Rebuilding or replacing it is blocked.                                                                           |
| Corrupt frozen request, unreadable identity, missing upsert record, invalid original base, or unresolved dependent conflict | No automatic replacement is inferred. The stored values remain available for inspection and recovery export.                                                                                            |

Selected recovery actions export recovery data before changing queue state. Cancelling or failing export leaves the queue unchanged. A review fingerprint detects record, outbox, failure, or revision changes during the save dialog; a stale review must be reopened.

SQL `23505` is not rollback proof: an operation UUID reused with another body can mean its original request already committed. New eligible rollback evidence is marked `rollbackProofVersion: 1`. Unversioned flags from Phase 5 remain uncertain and cannot authorize rebuilding or conflict replacement. Explicit retry retains the original UUID and body so the cloud can return its receipt or provide fresh rollback evidence.

Rebuilding stores the original operation chain, failures, and current record in a recovery copy before replacing the eligible operations. It validates the latest local record, preserves exact recorded allocation keys, retains the earliest original base revision, and uses a new operation UUID. Retaining that base lets an unseen cloud edit produce a conflict instead of being overwritten. A missing failed upsert is never interpreted as permission to delete; a deletion is rebuilt only when the latest queued intent explicitly requested deletion.

All repair writes occur in one Dexie transaction under the account worker's exclusive lock. Account and lifecycle guards run before and after the transaction work so sign-out or switching accounts rolls the operation back. A `wire_request` is treated as submitted even if its separate status field is damaged.

## Export format and scope

The full recovery envelope uses `format: "stride-recovery"`, `version: 1`. It includes the selected account's current workspace, pending operations, record revisions, cursor, all conflicts including resolved ones, all preserved recovery copies, and approved study-sync metadata. Export reads complete study tables instead of display indexes, so subjects, sessions, or copies with missing index fields remain included. `storedPreferences` and `storedTimers` also retain every raw row, including unexpected secondary rows. It does not read authentication storage, browser credentials, localStorage, another account database, or server administration values. The regular study-backup importer rejects this diagnostic envelope; importable history is exported separately with `format: "stride"`.

Ordinary JSON record shapes are retained. Values that JSON cannot represent use a `$strideRecovery` tagged object: decimal strings for BigInt, explicit undefined/nonfinite-number/array-hole tags, JSON-pointer references for cycles or repeated objects, Date/RegExp tags, Error name/message/stack/cause/custom properties, Map/Set entries, and base64 binary/Blob data. Raw malformed values are not normalized or discarded during export. Blob encoding happens after the consistent read transaction, with account-cancellation checks. A corrupt operation containing Blob data is quarantined without dispatch and offers only inspection/export; its file bytes cannot authorize an inferred rebuild or retry. Preserved-copy previews stop following nested recovery context after a bounded depth, so cyclic damaged data cannot hang inspection.

Stored error metadata contains a category, timestamp, and rollback proof. User-facing and persisted last-error summaries use fixed safe messages rather than raw network errors or bearer headers.

## Validation

The recovery unit suite executed **30/30 tests** successfully. Together with the touched existing storage/foundation/conflict/protocol/worker suites, the final targeted run executed **136/136 tests** successfully. TypeScript validation passed. Regression coverage includes missing index fields and secondary preference/timer rows, cyclic previews, Error and binary/Blob exports, oversized corrupt collections, immutable Blob requests, exact original null bases, SQL UUID-reuse uncertainty, and legacy unversioned rollback flags.

The final focused recovery browser suite executed **3/3 tests** successfully in 27.2 seconds. It exercises actual unchanged Phase 3 SQL through the isolated PGlite transport fixture and the ordinary React interface: export failure gating, new-UUID/current-record repair, deleted-session restoration with exact allocations through reviewed import, and corrupted frozen-request export without unsafe replacement. The device fixture now waits for account-database initialization before marking onboarding complete. Mocked SDK authentication in these browser tests is distinct from real Auth/PostgREST or packaged Windows verification.

Recovery copies remain device-local. Their availability does not replace a downloaded backup: clearing browser data, losing the device, or uninstalling a package can remove local storage. No claim of packaged file-dialog or packaged recovery behavior is made solely from unit/browser tests.
