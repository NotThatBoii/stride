# Phase 6: browser stress, network failures, timezones, and backups

This suite runs the real React application in Microsoft Edge, with independent browser contexts and IndexedDB account caches. Successful synchronization requests execute the unchanged Phase 3 migration in an isolated PGlite PostgreSQL fixture. Supabase Auth responses and network failures are controlled test responses. This is local browser/SQL coverage, not hosted Auth/PostgREST, physical devices, or packaged Windows validation.

Run `npm run test:e2e:stress`. The suite uses loopback port 1429, one worker, and disposable test accounts. It performs no hosted writes and does not change SQL, Auth settings, retention, or production records. The slow-response case deliberately waits for the application's actual 30-second request timeout.

Local result on 4 October 2026: **16 tests passed** in **2.2 minutes**. Exploratory runs found fixture timing issues (initial account initialization, CORS header exposure, and ownership of a browser timezone override); those were corrected before the completed run. They were not application defects or hosted failures.

| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Three-device stress           | Three independent account caches receive three sequential subject revisions. All three then edit a common subject and create independent histories offline. Concurrent synchronization calls preserve conflicting subject versions and converge on three sessions/six allocations after explicit conflict choices; the SQL receipt table contains no duplicate operation identities.             |
| HTTP 429                      | An unsent-to-SQL request remains frozen locally; the retry respects the supplied quarter-second `Retry-After` minimum and commits once with its original operation UUID.                                                                                                                                                                                                                         |
| HTTP 500, 502, 503            | Each status has a separate test. Local records and allocations remain intact, the worker reports a transient/offline condition, and a restored transport submits the original frozen request once.                                                                                                                                                                                               |
| Intermittent total offline    | Three actual browser offline/reconnect cycles each preserve a newly recorded local session, retain its outbox entry, drain the queue, and deliver the session/allocations to a second cache.                                                                                                                                                                                                     |
| Malformed response            | A success response with an impossible pull cursor is rejected without advancing the cursor, replacing local records, or discarding pending history. A healthy manual retry finishes.                                                                                                                                                                                                             |
| Aborted request               | A connection-reset failure leaves an immutable in-flight operation. Retry uses the original operation UUID and payload and creates one session/two allocations.                                                                                                                                                                                                                                  |
| Slow response/timeout         | The SQL pull response is held beyond the real 30-second timeout. The complete local page, cursor, and pending operation remain unchanged; releasing the delayed response and retrying pulls remote history and submits the local session.                                                                                                                                                        |
| Close during committed push   | The first SQL transaction commits while its acknowledgment is held. Closing the page and reopening the same browser profile restores its IndexedDB state, retries the same frozen request, and leaves one SQL receipt and one session.                                                                                                                                                           |
| Refresh during pull           | Reloading while a captured SQL page is held discards that old lifecycle's response. The restored account replays safely and receives its session and original allocations.                                                                                                                                                                                                                       |
| Sign-out during pull          | Signing out while a captured page is held, then entering a second account, prevents the late response from writing the second account's cache or exposing the first account's history.                                                                                                                                                                                                           |
| Expired token/refresh failure | An expired persisted session whose refresh is definitively rejected closes the authentication gate. Its account database and pending outbox survive; signing in again submits the preserved session. Test credentials never enter diagnostics or the application bundle.                                                                                                                         |
| Midnight, DST, and travel     | Three browser timezones (Asia/Manila, America/New_York, Europe/Berlin) record real allocations using `splitSegments`. Cases cover Manila/New York midnight, New York spring-forward/fall-back, and Berlin spring-forward. All cloud round trips retain the original day keys. Changing the first device to Berlin and reloading preserves them, and aggregate totals agree on all three devices. |
| Synced/older JSON backup      | An actual downloaded synced workspace export deduplicates on reimport without another cloud write. An older version-1 export with divergent same-ID session notes is staged and preserved before import, survives Cancel/reload, requires another backup download before continuing, preserves unrelated cloud history, and adds a separately identified copy only after Keep both.              |

An additional expired-token RPC test returns 401/PGRST303. It retains the study record and frozen operation, shows “Account needs attention,” and schedules no automatic retry. Official SDK refresh followed by retry submits the original operation UUID successfully. The 429 response explicitly exposes `Retry-After` through CORS so the browser can enforce its minimum wait; it does not rely on incidental test latency.

The common-subject conflict in the three-device case is resolved with an explicit choice to keep the cloud version. Its discarded device versions remain in conflict/recovery records. Independent session histories use their own subjects, so selecting a subject version does not imply selecting or cloning that subject's entire child tree. Parent delete/create races and late-child recovery also remain covered by the existing Phase 5 synchronization suite.

## Scope and limitations

- “Older backup” means a previously exported **supported version-1** backup. Stride has no implemented version-0 migration; an unsupported backup format must fail validation rather than receive invented migration rules.
- Browser offline flags, HTTP responses, dropped/held responses, and mock refresh rejection provide deterministic fault coverage. They do not model every operating-system suspension, captive portal, regional network, background tab throttle, or proxy behavior.
- Three contexts are three isolated logical devices on one Windows computer. They are not three physical machines. The timezone case changes the browser's timezone and verifies persisted allocations; it does not change the operating-system timezone.
- The PGlite fixture serializes SQL transactions. Concurrent browser calls exercise overlapping client lifecycles and the real RPC logic, but this is not a measurement of separate PostgreSQL server connections executing simultaneously.
- The actual 30-second timeout is measured with wall-clock bounds, not a fake timer. Other timings are test-control conditions, not performance benchmarks.
- Private study data remains in IndexedDB and the disposable SQL fixture. This suite neither tests nor changes hosted retention/pruning.

The final hardening report records the completed run and exact total alongside the separate mobile, recovery, PWA, native, hosted, and larger-workspace results.
