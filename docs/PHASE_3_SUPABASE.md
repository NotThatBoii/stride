# Phase 3 Supabase database and sync API

Phase 3 adds a versioned PostgreSQL migration and a server-side synchronization contract. It does **not** connect the Windows or web app to Supabase, authenticate users in the app, upload anonymous history, or apply the migration to the hosted project. The existing Dexie database remains the application's local source of truth.

The intended hosted project already exists: `fotgomkjwbahxmmovzmn` at `https://fotgomkjwbahxmmovzmn.supabase.co`. Read-only dashboard inspection verified that reference and URL, a Free plan, Healthy status, no entries shown in its migration list, and no tables or views in its `public` schema. No hosted schema change was made. Hosted migration is a separate, approval-gated step.

## Data model and migration

[`supabase/migrations/20260929000000_stride_sync.sql`](../supabase/migrations/20260929000000_stride_sync.sql) creates these tables. All keys are scoped by `owner_id uuid` referencing `auth.users(id)`; the server obtains this owner from `auth.uid()` rather than an operation payload.

| Table                                   | Key and relationship                                                         | Purpose                                                                                                                 |
| --------------------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `public.stride_subjects`                | `(owner_id, id)`                                                             | Subject fields from Dexie, including `archived` and original text ID.                                                   |
| `public.stride_sessions`                | `(owner_id, id)`; `(owner_id, subject_id)` references a subject              | Completed sessions with original text IDs and timestamps.                                                               |
| `public.stride_allocations`             | `(owner_id, session_id, day)`; `(owner_id, session_id)` references a session | One allocation per recorded local calendar day. `day` is PostgreSQL `date`; it is never derived again from server time. |
| `public.stride_preferences`             | `owner_id`                                                                   | Shared study goals: `minimum`, `goal`, `presets`, `week_start`.                                                         |
| `stride_private.stride_record_versions` | `(owner_id, entity, record_id)`                                              | Per-record revision and deletion marker, retained after a delete.                                                       |
| `stride_private.stride_sync_clocks`     | `owner_id`                                                                   | Serialized, per-account change sequence.                                                                                |
| `stride_private.stride_sync_changes`    | `(owner_id, sequence)`                                                       | Ordered upserts and tombstones for incremental pulls.                                                                   |
| `stride_private.stride_sync_operations` | `(owner_id, operation_id)`                                                   | Request hash and durable result for retry deduplication.                                                                |

Composite owner keys and foreign keys reject cross-account subject and session references even if a future client is faulty. A deferred constraint trigger checks that each session's allocation total matches its duration. Session upserts replace the session and its allocations in one transaction. A session operation accepts at most 1,000 daily allocations. Subject deletion explicitly deletes dependent sessions, emits their tombstones before the subject tombstone, and removes their allocations. Record versions remain after deletion so a stale create cannot resurrect a deleted record unnoticed.

The cloud payloads follow the current Phase 2 [`Subject`, `Session`, and `Slice`](../src/models.ts) shapes. Identifiers remain strings of 1–200 characters; this accommodates existing Dexie IDs without rewriting them to UUIDs. Timestamps use `timestamptz` and the RPC requires an explicit timezone offset or `Z`; older locally valid offset-less timestamps need normalization by the Phase 4 adapter. `archived` and `completed` retain their existing numeric flag shapes. `settings` has the fixed record ID `settings` and contains only `{minimum, goal, presets, weekStart}`. The Dexie settings fields `theme`, `notifications`, and `onboarded`, the active timer, recovery copies, and device-specific state remain local. The cloud change log contains study data and tombstones; the user's local Dexie `conflicts` and `recoveryCopies` sidecars preserve versions during future reconciliation.

This migration creates new cloud objects and does not read or modify existing IndexedDB data. It intentionally has no automatic history import. The original Stride V2 architecture audit was not present in this checkout. The implemented Phase 2 code and [`PHASE_2_SYNC_FOUNDATION.md`](PHASE_2_SYNC_FOUNDATION.md) are the compatibility reference. In particular, this design keeps account workspaces physically separate in Dexie, uses text IDs, preserves allocation day keys, and syncs only the shareable subset of settings.

## Security boundary

Every application table has Row Level Security enabled. Authenticated users have `SELECT` only on their own rows in the four public data tables. Anonymous callers have no table access. The private schema has no exposed table grants or RLS policies for client roles. Neither client role has direct `INSERT`, `UPDATE`, or `DELETE` grants on application tables.

Only `authenticated` can execute the two public RPC wrappers. They are `SECURITY INVOKER` functions; their implementation calls narrowly granted functions in `stride_private`. Those core functions are `SECURITY DEFINER`, use an empty `search_path`, qualify object names, reject missing `auth.uid()`, and apply explicit `owner_id` predicates. The private schema must **not** be added to the Supabase Data API's exposed schemas. Keep the public wrappers and underlying functions' execution grants under review when adding a new entity or endpoint. [Supabase's RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) and [database function](https://supabase.com/docs/guides/database/functions) guidance explain these boundaries.

The published project URL or a future publishable key does not authorize private data. RLS, SQL grants, and authenticated identity remain the authorization controls. Never put a secret, service-role key, database password, or personal access token into client code or an issue, PR, log, or chat.

## RPC contract

`public.apply_sync_operation(p_operation_id uuid, p_entity text, p_record_id text, p_action text, p_payload jsonb, p_expected_revision text) -> jsonb`

| Argument              | Contract                                                                                                                                                  |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `p_operation_id`      | Stable UUID from the Dexie pending operation. Retry the **same request** with the same UUID after a timeout. Reusing it with different input is rejected. |
| `p_entity`            | `subject`, `session`, or `settings`.                                                                                                                      |
| `p_record_id`         | Existing local record ID; settings uses `settings`.                                                                                                       |
| `p_action`            | `upsert` or `delete`. Deletes require a null payload.                                                                                                     |
| `p_payload`           | Exact subject object, `{session, slices}` object, or cloud settings subset on upsert. Ownership fields and unknown fields are rejected.                   |
| `p_expected_revision` | Decimal string of the last acknowledged server revision, or null only when no server version is known. This is not a local edit counter.                  |

An applied result is `{status: "applied", entity, record_id, action, revision: "…", cursor: "…"}`. A stale revision returns `{status: "conflict", entity, record_id, current_revision: "…" | null, deleted: boolean, current_snapshot: object | null}` without changing the study record. The operation ID retains that result for safe retry. A client that resolves the conflict must create a **new** operation ID with the chosen data and current revision. Invalid payloads, forged owner fields, missing subject references, or a changed request under an old operation ID fail rather than partially applying. Per-account clock locking serializes competing operations, so the first committed update advances the revision and later stale updates conflict.

`public.get_sync_changes(p_after text DEFAULT '0', p_limit integer DEFAULT 100) -> jsonb`

The cursor is a nonnegative decimal sequence string no higher than the account's current clock; page size is 1–500. The result is `{changes: [...], cursor: "…", has_more: boolean}`. Each change contains `sequence`, `entity`, `record_id`, `action`, `payload`, `revision`, and `operation_id`. Sequence, revision, and cursor values are decimal **strings** so JavaScript need not round PostgreSQL `bigint` values. Changes are ordered by per-account sequence, and delete entries carry a null payload. A session upsert includes its session and complete `slices` array as one change. On an empty page, the cursor remains the requested position.

The future client should pull pages until `has_more` is false, apply each page and advance its Dexie `syncCursors` value in the **same IndexedDB transaction**, then continue from the returned cursor. It must preserve server-reported conflicts and local pending data before asking the user to resolve a disagreement. There is no realtime subscription or cloud request in Phase 3.

## Local verification and migration procedure

From the repository root, `npm run test:db` runs the database contract tests under `supabase/tests/` against a fresh, isolated [PGlite](https://pglite.dev/docs/about) instance. The harness creates test-only Auth stand-ins and users, runs the checked-in migration, and verifies SQL constraints, simulated role and RLS behavior, RPC responses, retries, rollbacks, and pagination. It does not touch the hosted project. `npm test`, `npm run test:e2e`, and `npm run build` cover the existing app. Browser tests may regenerate tracked documentation screenshots; restore only those generated images after review.

PGlite does not reproduce the full Supabase Auth, PostgREST, or network stack and runs with a [single connection](https://github.com/electric-sql/pglite). Its tests cannot establish real multi-connection concurrency behavior. The repository also includes [real Auth and PostgREST integration tests](../supabase/tests/local-integration.mjs) for a disposable local Supabase stack. They cover anonymous denial, two-user isolation, table grants, RPCs, allocation rollback, retries, conflicts, pagination, tombstones, and concurrent network requests. These tests never target a hosted URL. The local stack uses the checked-in [`supabase/config.toml`](../supabase/config.toml), which exposes `public` and `graphql_public` through its Data API and keeps `stride_private` hidden. Realtime and unused local services are disabled. The Supabase CLI is pinned as a development dependency.

With Docker Desktop and WSL 2 installed and running on Windows, execute these commands from the repository root:

```sh
npm ci --legacy-peer-deps
npx --no-install supabase start
npx --no-install supabase db reset --local
npm run test:db
npm run test:integration
npm test
npm run build
```

The reset is **only for the disposable local database**. The `test:integration` runner privately calls the installed CLI's `status -o json`, verifies that its API URL is plain HTTP on `127.0.0.1` or `localhost` with an explicit port, and passes its local publishable/secret keys (or legacy anon/service-role keys) to the test process in environment variables. It never prints the CLI status or keys. The tests create two isolated local Auth users, sign in through Auth, call PostgREST with their tokens, and remove the users afterward. Do not paste keys into a command, source file, issue, log, or chat. Do not redirect raw `supabase status -o json` output into a shared file because it contains local keys. `supabase test db` is for pgTAP tests, if added; it does not run the JavaScript contract or integration tests. See [Supabase's local development](https://supabase.com/docs/guides/local-development/cli/getting-started) and [testing](https://supabase.com/docs/guides/local-development/testing/overview) guidance.

## Free-tier operation and Phase 4

The owner-scoped primary keys support point lookups; `(owner_id, subject_id)` supports a subject's sessions; `(owner_id, sequence)` supports ordered change retrieval. One account clock row serializes its writes, without persistent connections or realtime subscriptions. Each write also stores a change and an operation receipt, so history grows with usage. Do not prune either table until a cursor retention, stale-device recovery, and backup policy exists. Monitor database size and API usage in the dashboard; Supabase currently documents a [500 MB Free database size threshold](https://supabase.com/docs/guides/platform/database-size), which can change. Keep pages bounded and batch client pulls rather than polling continuously.

Phase 4 must add user-facing authentication, map the authenticated Supabase user UUID to the Phase 2 account workspace, and offer an explicit import/link decision for anonymous history. Its adapter must normalize offset-less legacy timestamps to explicit-offset ISO strings, canonicalize locally valid preset strings to comma-separated 1–4 digit integer values, and project only shared preference fields into cloud settings. Server conflict snapshots can render an equivalent timestamp with a different offset string, so compare instants rather than raw timestamp text. Its sync worker should submit account pending operations in order with their stable IDs and expected revisions, persist acknowledgments with `recordRevisions` and outbox removal atomically, retry `in_flight` entries unchanged, and pull pages into the same account database. Before sending a queued successor to an acknowledged operation for the same record, refresh its expected revision; never change an already-sent request under its operation ID. It must keep active timers and device settings local, preserve local and remote versions on conflict, and never show another account's cached data on sign-out or account switch. A coalesced local subject delete can precede pending child-session deletes; the server already emits child tombstones for that subject deletion, so a later child delete may receive a stale-revision conflict. Reconcile that conflict against the remote tombstone and retain recovery data where needed. Real Supabase Auth/PostgREST and concurrent-device tests are gates before activating synchronization.
