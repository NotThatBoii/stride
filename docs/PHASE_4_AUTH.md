# Phase 4 authentication and local account workspaces

> Authentication setup remains applicable. [Phase 5](PHASE_5_SYNC.md) now synchronizes account study history and provides explicit legacy/JSON import. The no-sync/import statements and test counts below record the Phase 4/4.1 boundary and do not describe the current Phase 5 client.

Phase 4 introduced email/password authentication through the official Supabase JavaScript client and account-scoped local workspaces. [Phase 4.1](PHASE_4_1_AUTH_REQUIRED.md) now requires authentication before entering Stride. This document describes the current setup and boundaries. Study data remains in IndexedDB on the current device. Signing in selects a separate local database for that Supabase account; it does **not** upload, download, reconcile, or synchronize study records. Signed-out users and builds without valid Supabase configuration cannot enter a study workspace. The Phase 3 PostgreSQL schema, policies, and RPCs are unchanged.

## Local setup

From the repository root:

```sh
npm ci --legacy-peer-deps
cp .env.example .env.local
npm run dev
```

On PowerShell, use `Copy-Item .env.example .env.local` instead of `cp` if preferred. Set `VITE_SUPABASE_URL` to `https://fotgomkjwbahxmmovzmn.supabase.co` and set `VITE_SUPABASE_PUBLISHABLE_KEY` to the project's **publishable** key from Supabase Dashboard → Project Settings → API Keys. The checked-in example contains placeholders only. Vite's `VITE_` variables are embedded in client assets, so never put a secret or service-role key, database password, personal access token, or admin credential in them. `.env` and `.env.*` are ignored by Git except `.env.example`. Restart Vite after changing environment variables. Missing, incomplete, or malformed configuration displays a clear configuration error and blocks workspace access. The client accepts this exact hosted project or a local Supabase URL; it does not create a guest fallback.

The production Cloudflare Pages build already has these public variables configured. New builds must retain them. For another build environment, set the same two `VITE_` variables before running Vite. The publishable key is public client configuration; do not use the secret key. Leave Preview unset unless a specific preview Auth flow and redirect URL have been approved; an unconfigured preview will show the configuration error. Vite embeds these variables at build time, so adding them after deployment does not change existing assets. [Cloudflare Pages build configuration](https://developers.cloudflare.com/pages/configuration/build-configuration/#environment-variables) documents the dashboard path.

Windows builds need the same public build-time configuration, including builds produced by GitHub Actions. Without it, the embedded frontend compiles but cannot authenticate or open a workspace. No runtime secret, new backend, expanded Tauri permission, or hosted Auth setting change is needed for the required entry flow.

## Authentication and workspace boundary

`src/lib/supabase.ts` creates the configured client with Supabase-managed session persistence and token refresh. `AuthProvider` restores the session on startup, listens for Auth state changes, and selects the workspace _before_ rendering study data. In `src/main.tsx`, `AuthGate` wraps the data `Provider` and `App`: restoration displays a loading state; signed-out or unconfigured states display authentication/configuration UI; only a signed-in user mounts the account data provider. The account's stored `onboarded` setting then determines whether the existing app shows two-step subject/Minimum Day onboarding or the main workspace. No initial guest welcome step or local continuation is present.

Stride does not copy tokens into its Dexie sync metadata or store passwords. On sign-out it writes the existing local signed-out marker and removes the SDK credential by storage key without reading its contents; this prevents an expired, offline session from reopening the account after a failed sign-out. A successful explicit sign-in clears the marker. An unexpired locally stored session can restore the account's local cache through the official client without network access. If an expired session cannot refresh, or initial restoration stalls, Stride shows an authentication error after at most eight seconds and blocks late restoration from reopening study data. There is no offline authentication bypass. Auth errors leave all local study records intact.

The unchanged `stride` IndexedDB database holds legacy anonymous history. A signed-in Supabase user with UUID `U` selects the separate `stride-account-U` database through Phase 2's `selectWorkspace(U)`. The account database records `owner_account_id` in its own metadata as a consistency guard. On sign-out, Stride removes the authenticated view synchronously, before any Auth request, and returns directly to authentication. The internal no-account workspace selection does not mount a data provider or open anonymous study data. An Auth error does not restore the account view. Switching to another account selects that account's distinct database. Token refresh for the same user leaves the selected workspace in place. The React data provider discards the previous workspace snapshot, subscribes to the new database, and remounts workspace-local UI state. This prevents the app from displaying one account's cached study records to another account. It is application-level separation within a browser or Windows profile, not device encryption or a defense against someone who can inspect that profile's IndexedDB files.

The entry screen offers sign-in and account creation with validation, loading, and error feedback. A sign-up response without a session shows an email-confirmation message and keeps the app at authentication; the user can return to sign-in after confirming. Settings and account onboarding offer the signed-in account status and sign-out. Neither displays guest access or anonymous-history decisions.

The entry flow does not open or scan the legacy `stride` database or the `stride-browser-preview-v1` localStorage dataset. It does not automatically migrate, copy, merge, upload, or delete that data. Existing legacy records and recovery data remain stored for an explicit Phase 5 import/recovery flow. JSON import/export and active timer recovery remain scoped to the selected account's local workspace. A running timer stays in its own account cache during sign-out, as it would during app closure; the account panel warns users to pause it if they do not want that time counted. Account mutations may continue to create Phase 2 pending operations locally, but neither Phase 4 nor Phase 4.1 processes or transmits that queue.

## Verification and limits

Run `npm test`, `npm run test:e2e`, `npm run test:e2e:auth`, and `npm run build` from the repository root. The dedicated Auth browser suite starts its own Vite process with a test-only publishable placeholder and intercepts Supabase Auth requests. It tests the UI and local workspace boundary without creating hosted users or study records. `npm run test:db` checks the unchanged Phase 3 SQL contract. `npm run test:integration` requires a disposable local Supabase stack and exercises the database RPC contract; it must never target the hosted project. See [Phase 3's testing instructions](PHASE_3_SUPABASE.md#local-verification-and-migration-procedure). Browser screen captures are written under ignored `test-results/`, leaving tracked documentation screenshots unchanged. A native Windows build can be attempted with `npm run desktop:build` when the Rust and Tauri prerequisites are installed. PR test results should report which of these commands actually ran and distinguish mocked Auth tests from a live hosted sign-in.

The Phase 4 dashboard inspection verified the hosted Site URL and default confirmation template; it did not test hosted sign-up/sign-in using disposable accounts. Mocked browser tests do not establish that hosted emails are delivered or a packaged Windows build can sign in. Report actual validation separately for each change. The signed-in local workspace is **not** a cloud backup: study records entered there stay on that device, and an account's local cache cannot be recovered on a new device yet. The account's cached IndexedDB data and Supabase-managed session storage are still accessible to someone who controls the same browser or operating-system profile. Signing out immediately hides the workspace; it does not erase that account's local cache or any legacy anonymous data.

## Phase 5 handoff

Phase 5 must define a reviewed, explicit anonymous-history import/link flow and build a sync worker for the selected account workspace only. It should adapt Phase 2 pending operations to `apply_sync_operation`, preserve their UUIDs for retries, acknowledge writes with per-record revisions atomically, pull `get_sync_changes` pages with cursor updates in the same Dexie transaction, and keep conflicts and recovery copies before resolution. It must normalize legacy timestamp offsets and shared settings payloads as described in [Phase 3](PHASE_3_SUPABASE.md#free-tier-operation-and-roadmap-handoff). Active timers and device settings stay local. Before enabling sync, test real Auth/PostgREST, multiple devices, sign-out during requests, offline recovery, and account switching without cross-account writes. Do not start a background worker or call either sync RPC for production study records in Phase 4 or Phase 4.1.
