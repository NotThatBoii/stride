# Phase 4 authentication and local account workspaces

Phase 4 adds optional email/password authentication through the official Supabase JavaScript client. Stride's study data remains in IndexedDB on the current device. Signing in selects a separate local database for that Supabase account; it does **not** upload, download, reconcile, or synchronize study records. Anonymous use continues without a Supabase configuration or network connection. The Phase 3 PostgreSQL schema, policies, and RPCs are unchanged.

## Local setup

From the repository root:

```sh
npm ci --legacy-peer-deps
cp .env.example .env.local
npm run dev
```

On PowerShell, use `Copy-Item .env.example .env.local` instead of `cp` if preferred. Set `VITE_SUPABASE_URL` to `https://fotgomkjwbahxmmovzmn.supabase.co` and set `VITE_SUPABASE_PUBLISHABLE_KEY` to the project's **publishable** key from Supabase Dashboard → Project Settings → API Keys. The checked-in example contains placeholders only. Vite's `VITE_` variables are embedded in client assets, so never put a secret or service-role key, database password, personal access token, or admin credential in them. `.env` and `.env.*` are ignored by Git except `.env.example`. Restart Vite after changing environment variables. To use Stride anonymously without a Supabase client, leave both variables empty or omit the local env file. Incomplete or malformed configuration disables cloud account controls without blocking local use; the client accepts this exact hosted project or a local Supabase URL.

For the production Cloudflare Pages build, set those same two `VITE_` variables under the existing Pages project's **Settings → Environment variables** for **Production**, then trigger a fresh build after the Phase 4 PR is merged. The publishable key is public client configuration; do not use the secret key. Leave Preview unset unless a specific preview Auth flow and redirect URL have been approved. Vite embeds these variables at build time, so adding them after deployment does not change existing assets. Until the production variables are set and rebuilt, account controls remain disabled on the deployed site. [Cloudflare Pages build configuration](https://developers.cloudflare.com/pages/configuration/build-configuration/#environment-variables) documents the dashboard path.

## Authentication and workspace boundary

`src/lib/supabase.ts` creates the optional client with Supabase-managed session persistence and token refresh. `AuthProvider` restores the session on startup, listens for Auth state changes, and selects the workspace _before_ rendering study data. Stride does not copy tokens into its Dexie sync metadata. On sign-out it writes a small local signed-out marker and removes the SDK credential by storage key without reading its contents; this prevents an expired, offline session from reopening the account after a failed sign-out. A successful explicit sign-in clears the marker. An unexpired locally stored session can restore the account's local cache without network access. If an expired session cannot refresh, or initial restoration stalls, Stride falls back to the anonymous workspace after at most eight seconds and blocks a late session event from changing the visible workspace. Auth errors leave local study records intact; the account cache remains on the device. Local anonymous use remains available when signed out.

The unchanged `stride` IndexedDB database is anonymous. A signed-in Supabase user with UUID `U` selects the separate `stride-account-U` database through Phase 2's `selectWorkspace(U)`. The account database records `owner_account_id` in its own metadata as a consistency guard. On sign-out, Stride selects the anonymous database synchronously, before any Auth request; an Auth error does not restore the account view. Switching to another account selects that account's distinct database. Token refresh for the same user leaves the selected workspace in place. The React data provider discards the previous workspace snapshot, subscribes to the new database, and remounts workspace-local UI state. This prevents the app from displaying one account's cached study records in another account or in anonymous mode. It is application-level separation within a browser or Windows profile, not device encryption or a defense against someone who can inspect that profile's IndexedDB files.

Settings offers sign-up, sign-in, sign-out, status, and the current email, with loading and error feedback. The onboarding screen also provides account access before a new workspace is configured. If anonymous study records or an active timer exist after sign-in, Stride asks the user to keep that history separate or prepare a future import. Both choices preserve the anonymous database; “prepare” records only a decision in that account's local `syncMetadata`. The prompt remains resolved for that account on later sign-ins. No Phase 4 code copies anonymous records into the account or sends them to Supabase. JSON import/export and active timer recovery remain scoped to the selected local workspace. A running timer continues in its own workspace during account switching, as it would during app closure; the account panel warns users to pause it if they do not want that time counted. Account mutations may continue to create Phase 2 pending operations locally, but Phase 4 never processes or transmits that queue.

The Tauri `connect-src` permits the exact `https://fotgomkjwbahxmmovzmn.supabase.co` origin alongside its existing IPC origins; it does not use a wildcard. ## Verification and limits

Run `npm test`, `npm run test:e2e`, `npm run test:e2e:auth`, and `npm run build` from the repository root. The dedicated Auth browser suite starts its own Vite process with a test-only publishable placeholder and intercepts Supabase Auth requests. It tests the UI and local workspace boundary without creating hosted users or study records. `npm run test:db` checks the unchanged Phase 3 SQL contract. `npm run test:integration` requires a disposable local Supabase stack and exercises the database RPC contract; it must never target the hosted project. See [Phase 3's testing instructions](PHASE_3_SUPABASE.md#local-verification-and-migration-procedure). Browser tests may regenerate tracked documentation screenshots; review those artifacts before keeping them. A native Windows build can be attempted with `npm run desktop:build` when the Rust and Tauri prerequisites are installed. Test results for the Phase 4 PR should report which of these commands actually ran and distinguish mocked Auth tests from a live hosted sign-in.

The hosted Auth URL correction remains an approval-gated configuration change. Until it is made, confirmation emails may send users to the current `localhost:3000` fallback. Hosted sign-up and sign-in using disposable accounts have not been verified by this document. The signed-in local workspace is **not** a cloud backup: study records entered there stay on that device, and an account's local cache cannot be recovered on a new device yet. The account's cached IndexedDB data and Supabase-managed session storage are still accessible to someone who controls the same browser or operating-system profile. Signing out changes the app's visible workspace; it does not erase that account's local cache.

## Phase 5 handoff

Phase 5 must define a reviewed, explicit anonymous-history import/link flow and build a sync worker for the selected account workspace only. It should adapt Phase 2 pending operations to `apply_sync_operation`, preserve their UUIDs for retries, acknowledge writes with per-record revisions atomically, pull `get_sync_changes` pages with cursor updates in the same Dexie transaction, and keep conflicts and recovery copies before resolution. It must normalize legacy timestamp offsets and shared settings payloads as described in [Phase 3](PHASE_3_SUPABASE.md#free-tier-operation-and-roadmap-handoff). Active timers and device settings stay local. Before enabling sync, test real Auth/PostgREST, multiple devices, sign-out during requests, offline recovery, and account switching without cross-account writes. Do not start a background worker or call either sync RPC for production study records in Phase 4.
